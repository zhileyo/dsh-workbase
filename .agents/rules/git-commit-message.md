# Git Commit Message 规范

提交信息有两个用途：给人读，以及让 `semantic-release` 从 type 推断该发哪个版本号。**改 type 名或分隔符时，必须同步 `release.config.mjs` 里的 `headerPattern` / `releaseRules`**，否则发版会静默降级成不发版。

## 提交格式

```text
<type>：<subject>

1.原因分析：<原因，无则填「无」>
2.修改方法：
1）<具体修改点>
2）<具体修改点>
```

- type 后接全角冒号「：」，不空格，直接接 subject
- 需要标注作用域时写 `type(scope)：subject`（半角括号、可选，如 `问题修复(composer)：…`）
- subject 一句话概括本次提交，简短且看得懂，把版本号写在里面（如 `新增文件：0.3.0 …`）
- body 固定「原因分析 + 修改方法」两项，子项用 1）2）3）编号
- type 按 diff 主体内容归类；混合变更按**主体**归类，无法归类时用「其他提交」

## type 与发版级别

| type | 语义 | 本仓库典型场景 | 版本号 |
| --- | --- | --- | --- |
| 新增文件 | 只加能力，不动既有对外契约 | 新增视图、服务端接口、Agent 工具、测试文件 | minor |
| 代码重构 | 只改内部结构、修复与宿主的对接，或改坏对外契约 | 抽公共模块、合并重复逻辑、拆函数、调整目录（先用测试证明等价）；修复宿主对接（见下段）；**破坏性改动**：删改 zod 字段、RPC 频道名、Agent 工具参数、存储域／键、宿主接线方式 | major |
| 问题修复 | 修缺陷，接口不变 | 修渲染、排序、交互、边界判定 | patch |
| 编译代码 | 构建、配置、依赖 | `build.mjs`、`sync-ui.mjs`、`release.config.mjs`、devDependencies | patch |
| 文档修改 | 只改文字 | `README.md`、`docs/`、`.agents/notes/` | patch |
| 样式修改 | 不影响行为的改动 | CSS 数值微调、格式化、缩进 | 不发版 |
| 其他提交 | 以上之外的杂项 | 重命名、移动文件、清理仓库、重建仓库 | 不发版 |

判定顺序：**先问「对外承诺改坏了没有」**——是 → 「代码重构」（major；破坏性改动在 body 首句写明「不兼容」及受影响方）。再问「加了能力没有」——是 → 「新增文件」（minor）。再问「是不是只动内部结构、或只在修与宿主的接线」——是 → 「代码重构」（major）。剩下的按 patch 处理。改动量大小不决定版本号。

宿主对接（上表「见下段」指的就是这里）与插件内部要分清：插件跑在宿主里，但两边的毛病归不同 type——**接线层**（slots 注入、能力探测与降级、注册到宿主的存储域／RPC／HTTP／工具、`cordis.patch.yml`、peer 依赖）出问题算「代码重构」；**插件自己的渲染、排序、交互**出问题仍算「问题修复」。

0.x 期间 major 的落点就是 1.0.0：破坏性改动或结构大改一旦提交，版本会从 0.3 直接跳到 1.0.0，中间的小版本不再出现。发 1.0.0 之前先确认这条映射还成不成立——若不想让一次重构顶到稳定版，把 `release.config.mjs` 里 `代码重构` 的 `release` 改成 `minor`，让它退化成 0.4.0 那样的递增。

## subject 规则

- 【问题修复】简要描述**现象与影响**，不要写实现细节
- 批量导入、结构性大改应拆成多个提交，便于审核与回溯
- 不写「更新了一些文件」这类无信息量的主语

## body 规则

- 说清原因与具体改法，让半年后的自己能重建当时的判断
- 【问题修复】必须填写原因分析；其他类型可填「无」
- 修改点多时用 1）2）3）逐条列出，一条一个可验证的动作

## 示例

```plain
问题修复(composer)：0.3.0 分支条在窄面板下挤出输入框

1.原因分析：分支条用了视口断点，面板收窄到 420px 时仍按宽屏排布
2.修改方法：
1）把该断点改成容器查询
2）在 test/prototype-css.test.ts 补一条不变量断言
```

```plain
问题修复：0.3.0 待办排序改为按最近更新

1.原因分析：原按创建时间排序，与 PRD 的「最近更新倒序」不一致
2.修改方法：
1）service 层改排序字段
2）PRD 与开发日志同步改写
```

```plain
文档修改：补齐 AGENTS.md 的发布边界

1.原因分析：发布前的复查步骤只写在已删除的检查文档里
2.修改方法：
1）新增「发布边界与复查」一节
2）自检清单加一条
```
